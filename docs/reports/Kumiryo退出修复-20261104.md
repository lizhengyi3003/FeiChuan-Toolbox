# Kumiryo 退出与备份状态修复 · 1.5.6

## 原因和证据

用户提供的失败日志来自测试电脑。原工作进程已是管理员，失败停在退出阶段，未执行设置写入；原始 DPAPI 副本可解密，当前文件与初始副本一致。客户端 minimizeOnExit=true，正常窗口关闭会收起到托盘。

旧策略先发送 WM_CLOSE，等待后投递 WM_QUIT。线程退出消息不能代表完整 Flutter 客户端按正常流程退出。相同退出时段的 Windows Application Error 记录 kumiryo.exe / flutter_windows.dll，异常 c0000005 与 c000041d；旧日志没有逐条消息结果，不能仅凭时间关系宣称某一条消息是唯一原因。

## 修复边界

移除 WM_QUIT。已知关闭收起托盘时不发送无效关闭请求。应用和恢复预览提供界面退出兜底选项，授权只属于本次操作；旧记录无此字段时默认为未授权。

兜底须先核验初始 DPAPI 备份、JSON 与保存稳定性，再持有并复核进程句柄、映像路径、账户、会话和创建时间。只结束该客户端界面，不结束进程树，不调用内核或服务停止接口；未保存的界面状态可能丢失，客户端自身行为也可能影响代理，预览对此说明。

初始备份解密读回后单独标记 InitialBackupReady；稳定原始/目标设置的写入恢复备份用 BackupReady 表示。退出策略、错误码和兜底使用情况均记录。未授权、备份不符、配置仍在保存或身份变化时停止写入。

## 验证

原模拟客户端只通过 GetMessage 收到 WM_QUIT 后退出，不能代表真实 Flutter。新夹具明确忽略该消息并收起到托盘，验证未授权时保留原进程和设置、授权后精确退出/写入/重开，以及恢复和中断保护。136 项功能检查、普通权限 10 项和管理员 11 项 Sandbox 检查通过。

独立测试目录中的修复 Core 完整哈希与真实客户端只读预检通过。用户后续明确确认“一键配置成功完成，重新打开正常”，按用户实机验收通过记录；没有将其等同于完整内核运行读回。开发机现用客户端和网络没有作为可丢弃夹具。

私人设备标识、操作编号、PID、原始日志、配置和加密备份保存在忽略目录，不随源码或软件分发。当前边界见 [验收记录](../VALIDATION.md)。
