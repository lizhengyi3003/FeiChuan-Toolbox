# 数据恢复、全局设置与诊断

1.4.1 在窗口顶部提供全局设置，启动管理、兼容热点及 Kumiryo 一键配置都可进入。外观、窗口、托盘和通知使用当前账户的 `preferences.json`，不再通过扫描数据库保存。主文件损坏时尝试上一份有效设置，并保留损坏原件。

诊断记录独立保存在 `diagnostics`。界面显示操作、错误编号、时间、版本、Windows/SQLite 错误码、处理建议及日志路径。页面读取失败有可重试的兜底页；设置页可查看最近记录。主目录不可写时尝试当前用户私有的临时目录；都不可写时明确提示复制界面详情。常见 token、password、Authorization 和 API key 被过滤，不自动上传日志。

重试只重新读取页面或核验数据库。启停、注入、恢复等操作仍需重新预览与确认，不因报错自动重复。运行中发现 SQLite 11/26 会暂停本地监测和读写，后台机器服务独立运行。初始化失败保留原诊断窗口；不能安全继续的底层故障仅尽力记录，不能承诺所有硬件错误或进程强制终止都有可见窗口。

本次恢复在原库副本上使用经官方 SHA3 校验的 SQLite 提取工具，关闭已确认的旧界面/分析连接后离线替换。候选由程序已知结构重建，并使用当前 Core 模型校验；不安装提取出的未知表、执行 SQL 或损坏 JSON。原件、旁文件、被排除的记录及操作回执保存在本机受限备份目录，不进入分发包。

恢复候选包含 5 份本机有效快照、3,635 条事件、8 条提醒、382 项分析和 436 条分析历史。分析来自本机已有导出；不匹配当前指纹的建议不会当作当前有效结论。恢复的最新快照有 1,293 个历史入口，并标记等待复扫。3 份缺失正文的快照、无法解析的最新指针及身份不匹配的旧快照没有直接导入。无法保证所有历史均完整找回。

修复前确认所有旧数据库连接退出；维护锁阻止新版本建立新连接，文件替换前还核对原件哈希及残留句柄。替换失败保留备份并尝试恢复原文件；替换后的完整性检查、实际启动和复扫回读，以本机修复回执为准。

本机逻辑 AppData 路径的文件实际位于 D 盘缓存目录。修复按句柄返回的真实位置完成，并保留原加密属性。1.4.2 同时修复这个环境下应用设置重复保存失败的问题，补充连续三次真实加密文件保存检查。路径映射与加密共同出现并不足以证明它们是此前数据库损坏的唯一原因。

参考：[SQLite 恢复及其限制](https://www.sqlite.org/recovery.html)、[SQLite 并发替换与日志配对风险](https://www.sqlite.org/howtocorrupt.html)、[Microsoft.Data.Sqlite 连接池](https://learn.microsoft.com/en-us/dotnet/standard/data/sqlite/connection-strings)。现有证据不足以单独认定 EFS、某个管家或某次操作就是损坏原因。
